# 怎样证明检查真的有效
[返回首页](../README.md)

## 不要只证明“按钮能点”
安装成功 → 能运行 → 能发现预设问题 → 修复后问题消失 → 重复结果稳定 → 扫描不修改资源，是不同层次的证据。

## 在隔离的测试项目中验证
不要为测试破坏正式资源。先创建副本或独立分支，记录 Unity 版本、Localization 版本和插件完整提交号。

| 用例 | 操作 | 应核对 |
| --- | --- | --- |
| 正常对照 | 准备两种语言、内容完整的测试表 | 对照词条不出现漏项/空值错误 |
| 空翻译 | 将其中一个现有词条的翻译设为空 | 空翻译规则报告准确的表、语言、词条 |
| 缺词条 | 保留 Shared Data 中的键，仅删除某语言表内条目 | 完整性规则报告该语言缺项；不要误删所有语言共享键 |
| 坏引用 | 在测试预制体中引用有效词条，再使该引用失效 | 引用规则报告预期组件/属性 |
| 修复复查 | 只修复上述预置问题 | 对应问题消失，其他问题不会被顺带隐藏 |

每次只改变一个变量，记录“修改前、预期、实际、修复后”。字符串表编辑操作需确认到底是在删除某语言条目，还是共享键。

当前窗口需至少一个已保存的 Scene/Prefab 目标才能启动。测试表问题不要求定位按钮可用；另用预制体问题验证定位。字体检查需要独立配置验证，窗口未验证结果不能算字体测试通过。

## 重复性
相同数据连续扫描三次，对比规则、资源、对象、问题内容及排序。不要把耗时或时间戳算入问题签名。运行完成状态和诊断也要记录。

## 非修改性
1. 等待首次导入和编译完成后再建立基线。
2. 对 Assets、Packages、ProjectSettings 的受版本控制文件记录哈希及场景 dirty 状态。
3. 仅运行扫描，不执行定位、修复或手动保存。
4. 对比扫描后哈希、场景状态和已加载场景集合。
5. 将导入器造成的改动与扫描造成的改动分开调查。

## 自动测试
在仓库宿主项目中使用 Unity Test Runner 执行 EditMode 测试，保留 XML 和 Editor 日志。包测试未显示时，检查宿主的 testables 配置是否包含 com.yxwm.localization-auditor。
无界面的 batchmode 测试不能替代真实 GUI 操作；任何跳过项都应解释。

**60 条样本目录不等于 60 次真实规则执行。** 必须检查测试是否创建输入、调用规则并断言结果。
